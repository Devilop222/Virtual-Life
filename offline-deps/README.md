# 📦 نصب آفلاین — میراث (Legacy Game)

این پوشه **همهٔ پیش‌نیازهای اجرای ربات** را بدون نیاز به اینترنت دارد:

| فایل | توضیح |
| :--- | :--- |
| `install.sh` | نصب‌کنندهٔ یک‌دست — فقط همین یک اسکریپت را ران کنید |
| `node_modules-linux.tar.gz` | تمام وابستگی‌های برنامه (Node.js — هم x64 هم arm64) |
| `dist.tar.gz` | کدهای کامپایل‌شدهٔ ربات |
| `postgres-linux-x64.tar.gz` / `postgres-linux-arm64.tar.gz` | PostgreSQL آماده‌ی اجرا (دیتابیس داخلی) |
| `node-v22.22.3-linux-x64.tar.xz` | خود Node.js (نسخهٔ آفلاین) |
| `scripts/migrate.js` | مهاجرت‌ساز آفلاین دیتابیس |
| `scripts/db-setup.js` | سازندهٔ دیتابیس |

> 🔌 تنها چیزی که به اینترنت نیاز دارد **کپی کردن خود مخزن از GitHub** است (یک‌بار).
> بعد از آن، هیچ چیزی از اینترنت دانلود نمی‌شود.

## ✅ قبل از شروع: دو چیز لازم دارید

### ۱) توکن ربات تلگرام (BOT_TOKEN)

1. در تلگرام به کاربر `@BotFather` بروید.
2. اگر هنوز ربات نساخته‌اید: پیام `/newbot` بدهید و دو اسمی که می‌خواهد را بنویسید.
3. اگر ربات را قبلاً ساخته‌اید: `/mybots` → ربات را انتخاب کنید → **API Token**.
4. چیزی شبیه `123456789:AAH...` می‌دهد — **این را کپی کنید** (بعد لازم می‌شود).

### ۲) توکن خواندنی GitHub (فقط برای کپی کردن مخزن)

مخزن خصوصی است، پس یک توکن سراسری با دسترسی **فقط‌خواندنی** بسازید:

1. وارد [github.com/settings/tokens](https://github.com/settings/tokens) شوید (با حساب خودتان).
2. سمت چپ: **Fine-grained tokens** → **Generate new token**.
3. Name: هر چیز دلخواه (مثلاً `virtual-life-server`).
4. **Expiration**: مثلاً ۳۰ روز (هر وقت تمام شد بسازید؛ یا «No expiration»).
5. **Repository access**: فقط **Only select repositories** → مخزن `VirtualLife`.
6. **Permissions → Repository permissions**: فقط `Contents` را روی **Read only** بگذارید. بقیه دست نزنید.
7. **Generate token** → توکنی که می‌دهد را **بکاپ بگیرید** (دومین بار که صفحه بسته شود، دیگر دیده نمی‌شود).

> 🔒 **ایمنی:** این توکن فقط «خواندن» همان یک مخزن را دارد. آن را در جای امن نگه دارید و با هیچ‌کس (حتی چتbotها و هوش مصنوعی) به اشتراک نگذارید.

## 🚀 نصب روی سرور (Daytona / هر لینوکسی)

در ترمینال سرور، این سه خط را اجرا کنید (در خط اول، `GITHUB_TOKEN` را با توکن GitHub جایگزین کنید):

```bash
git clone https://GITHUB_TOKEN@github.com/aminatkh0-ship-it/VirtualLife.git
cd VirtualLife
git remote set-url origin https://github.com/aminatkh0-ship-it/VirtualLife.git   # حذف توکن از تنظیمات
bash offline-deps/install.sh
```

اسکریپت از شما فقط یک چیز می‌خواهد: **توکن ربات** (همان آیتم ۱). بقیه خودکار است:

- Node.js پیدا یا نصب می‌شود
- دیتابیس داخلی PostgreSQL ساخته و راه می‌افتد (پورت 5432، یا اگر اشغال بود اولین پورت آزاد)
- تمام جدول‌ها و داده‌های اولیه (شغل‌ها و مهارت‌ها) اعمال می‌شود
- ربات اجرا می‌شود و آدرس اتصال در `.env` ثبت می‌شود

در پایان پیام سبز «همه‌چیز آماده است!» می‌آید. به ربات تلگرامتان `/start` بدهید. ✅

### اگر دیتابیس خارجی دارید (Supabase / Neon / Railway / ...)

قبل از اجرای اسکریپت، یک بار این کار را انجام دهید:

```bash
git clone ...   # همان دو خط قبل
cd VirtualLife
nano .env       # یا هر ویرایشگر دیگری
```

و این خط را در فایل `.env` جایگزین کنید (با آدرس واقعی دیتابیس خودتان):

```
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DBNAME
```

بعد `bash offline-deps/install.sh` را بزنید — دیتابیس داخلی ساخته **نمی‌شود** و از همان خارجی استفاده می‌کند.

## 🧰 دستورات روزمره

همه از داخل پوشهٔ پروژه (`~/VirtualLife` یا هر جایی که clone کرده‌اید):

| دستور | کار |
| :--- | :--- |
| `bash offline-deps/install.sh status` | وضعیت ربات و دیتابیس |
| `bash offline-deps/install.sh stop` | خاموش کردن ربات **و** دیتابیس |
| `bash offline-deps/install.sh start` | روشن کردن دیتابیس و ربات |
| `tail -f .tools/bot.log` | مشاهدهٔ زندهٔ لاگ ربات (خاموش با `Ctrl+C`) |
| `bash offline-deps/install.sh update` | بعد از `git pull`: اعمال مهاجرت‌ها + رستارت |
| `bash offline-deps/install.sh restore <id>` | بازگرداندن دادهٔ بازی از یک بکاپ (خاموش → بازیابی → روشن → سلامت) |
| `bash offline-deps/install.sh reset --yes` | پاک‌سازیِ کاملِ وضعیتِ ربات (دیتابیس، لاگ، بکاپ، PID/قفل، dist) و آماده‌سازی برای نصبِ دوباره |

**آپدیت ربات:**

```bash
cd VirtualLife
git pull origin main
bash offline-deps/install.sh update
```

### هدفِ دیتابیس — یک قاعده

`install` / `update` / `start` / `restore` هدفِ دیتابیس را **فقط** از این دو جا
می‌خوانند، به این ترتیب:

1. `--url=postgresql://…` روی خط فرمان (صریح‌ترین حالت)
2. `DATABASE_URL` داخل `.env`

**متغیرِ محیطیِ شل هیچ‌وقت هدف را عوض نمی‌کند.** اگر بگذارید، یک هشدار
می‌گیرید (آدرسِ محیطی و آدرسِ هدف چاپ می‌شود) ولی کار با همان آدرسِ `.env` انجام
می‌شود. دلیلش یک باگِ واقعی است: یک `export DATABASE_URL="…:5433…"` جامانده در
ترمینال، `db-setup.js` را روی پورتی می‌فرستاد که هیچ‌کس آن‌جا گوش نمی‌داد و نصب با
`connect ECONNREFUSED` می‌مرد — درحالی‌که دیتابیسِ درست روی ۵۴۳۲ بالا آمده بود.

```bash
# هدف‌گرفتنِ دیتابیسِ دیگری برای همین یک اجرا (بدون دستِ بردن به .env):
bash offline-deps/install.sh --url=postgresql://user:pass@host:5432/dbname
```

> ابزارهای راستی‌آزمایی (`scripts/*-smoke.cjs`) برعکس عمل می‌کنند و عمداً
> متغیرِ محیطی را محترم می‌شمارند (`DATABASE_URL=… node scripts/…`)، چون کارشان
> اجرا روی یک دیتابیسِ **آزمایشی** است، نه روی دیتابیسِ نصب. همین باعث می‌شود
> آدرسِ آزمون را با `export` سراسری ندهید؛ زیرپوسته یا پیشوندِ همان‌خط را بگذارید
> تا نصبِ بعدی آن را به ارث نبرد.

> اگر آپدیت، وابستگی‌های جدید می‌خواست (ریپکِج)، بگویید تا بستهٔ آفلاین را در همین مخزن به‌روز کنم.

## 💾 بکاپ و بازیابی

برداشتن بکاپ و بازیابی از بکاپ از داخل خود ربات و توسط **مالک اصلی** انجام می‌شود:
`/botupdate` در چت خصوصی → «مرکز کنترل» → «بکاپ‌ها».

| کار | از کجا |
| :--- | :--- |
| برداشتن بکاپ | «بکاپ‌ها» → «بکاپ تازه» — بازی قطع نمی‌شود |
| بررسی سلامت | ماندن روی فهرست یا «بررسی همه» |
| بازیابی | یک بکاپ → «بازیابی این بکاپ» → «تأیید بازیابی» (دو تأیید) |
| پاک‌سازی | «پاک‌سازی قدیمی‌ها» — جدیدترین و آخرین بکاپِ ایمنی نمی‌روند |

بکاپ‌ها کنار خود پروژه در `.tools/backups/` می‌نشینند (همان جایی که دیتابیس است).
دستورِ `restore` هم برای زمانی است که ربات بالا نمی‌آید و باید از ترمینال بازیابی کنید؛
شناسهٔ بکاپ همان نام پوشهٔ آن در `.tools/backups/` است.

> روی این سرور `pg_dump` وجود ندارد (بستهٔ داخلی PostgreSQL فقط `initdb`، `pg_ctl` و
> `postgres` دارد). پس بکاپ به‌جای ابزارِ بیرونی، از خودِ موتورِ دیتابیس کدگذاری می‌شود
> و هیچ وابستگیِ تازه‌ای نمی‌خواهد.

## 🩺 عیب‌یابی

| مشکل | راه‌حل |
| :--- | :--- |
| نصب با `connect ECONNREFUSED 127.0.0.1:XXXX` می‌میرد و آن پورت هیچ‌جای کد نیست | یک `export DATABASE_URL=…` جامانده در ترمینال است. `unset DATABASE_URL` بزنید و دوباره نصب کنید؛ نصب‌کننده از این پس فقط `.env` (یا `--url`) را قبول می‌کند و در صورت تعارض، خودش هشدار می‌دهد |
| پورت 5432 اشغال است (Postgres سیستمی / Docker / سرویس دیگر) | نسخهٔ فعلی **خودکار** اولین پورت آزاد (تا 5532) را برمی‌دارد، در `.tools/.pgport` و `DATABASE_URL` ثبت می‌کند، و start/status همان را به کار می‌برد. برای اجبار پورت مشخص: `PG_PORT=5433 bash offline-deps/install.sh` — اگر همان هم اشغال باشد اسکریپت خطا می‌دهد تا پورت اجباری‌تان دزدیده نشود |
| اجرای اسکریپت با **root** | مشکلی نیست — اسکریپت خودش خودکار یک «کاربر سرویس» سیستمی به نام `postgres` می‌سازد (بدون شل ورودی و بدون خانه در `/home`) و **فقط دیتابیس** را با آن اجرا می‌کند؛ بقیهٔ مراحل با همان کاربر شماست. اگر کاربر سرویس از قبل ثبت شده باشد (`.tools/.pguser`) همان را ادامه می‌دهد |
| ربات بالا امد ولی در تلگرام جواب نمی‌دهد | توکن اشتباه است؛ `.env` را ویرایش کنید، `BOT_TOKEN` را درست کنید و `bash offline-deps/install.sh start` |
| ربات در **گروه** متن‌ها را نمی‌بیند | Privacy Mode ربات خاموش است: @BotFather → `/mybots` → **Group Privacy** → **Turn off** |
| خطای `401 Unauthorized` در لاگ | توکن ربات بی‌اعتبار/اشتباه است |
| سرور arm64 است ولی Node پیدا نمی‌شود | اگر اینترنت دارد، اسکریپت خودکار با `apt` نصب می‌کند؛ در غیر این صورت سندباکس را از تصویر (image) Node.js بسازید |
| لاگ دیتابیس | `cat .tools/pg.log` |

## 🔐 نکات امنیتی

- توکن‌ها فقط در فایل `.env` (که در git commit **نمی‌شود**) ذخیره می‌شوند.
- اسکریپت هیچ‌وقت توکن GitHub شما را نمی‌خواهد و ذخیره نمی‌کند؛ توکن فقط در فرمان `git clone` یک‌بار استفاده می‌شود و همان خط `git remote set-url` آن را از تنظیمات پاک می‌کند.
- دیتابیس داخلی فقط روی `127.0.0.1` گوش می‌دهد — از خارج سرور قابل دسترسی نیست.

## 🛠️ برای توسعه‌دهنده

بسته‌های آفلاین با `packaging.sh` (در همین پوشه) ساخته می‌شوند — روی دستگاهی با دسترسی به npm اجرا شود:

```bash
bash offline-deps/packaging.sh
```

تغییرات مهمی که برای این جریان در پروژه اعمال شده:

- `prisma/schema.prisma`: `engineType = "client"` — کلاینت Prisma با موتور WASM (بدون باینری پلتفرم‌وابسته؛ x64 و arm64 یکسان).
- `src/database/client.ts` و `prisma/seed.ts`: اتصال از طریق **driver adapter** (`@prisma/adapter-pg` + درایور `pg`) — همان دلیل بالا.
- `offline-deps/scripts/migrate.js`: مهاجرت‌های SQL را با `pg` اعمال می‌کند و در `_prisma_migrations` با فرمت دقیق Prisma 6.19 ثبت می‌کند (سازگار با CLI).
- رفع دو باگ مهاجرت‌ها که نصب تازه را شکست می‌داد: BOM در ابتدای `migration.sql` اولیه و `CREATE TYPE "MigrationReason"` تکراری (اکنون ایدامپوتنت است).

### چه بسته‌ای را کِی باید دوباره ساخت

`install.sh` روی سرور فقط دو بسته را باز می‌کند و **هرگز `prisma generate` اجرا نمی‌کند**؛ پس کلاینتِ ساخته‌شدهٔ Prisma داخل `node_modules-linux.tar.gz` منتشر می‌شود:

| تغییر | بستهٔ لازم |
| :--- | :--- |
| هر تغییر کد (`src/`، `prisma/seed.ts`) | `dist.tar.gz` |
| تغییر `prisma/schema.prisma` (مدل/فیلد/مهاجرت تازه) | `node_modules-linux.tar.gz` **و** `dist.tar.gz` |
| تغییر وابستگی‌ها (`package.json`) | `node_modules-linux.tar.gz` |

اگر فقط اسکیما عوض شود و بستهٔ `node_modules` بازسازی نشود، کلاینتِ کهنه منتشر می‌شود و سرور بدون اینترنت در زمان اجرا با «مدل ناشناخته» یا «Unknown argument» می‌شکند.

### 🔒 دروازهٔ هم‌خوانیِ کلاینتِ Prisma (ضدِ همین اشتباه)

این اشتباه یک بار واقعاً رخ داد: `dist.tar.gz` چند بار بازسازی شد ولی
`node_modules-linux.tar.gz` از یک کامیتِ قدیمی‌تر ماند؛ نتیجه این شد که کلاینتِ داخل بسته
مدل `ProjectDonation`، ستون‌های `Player.lives`/`healthSyncedAt` و چند مقدارِ enum را
نمی‌شناخت. نصب **بی‌خطا** تمام می‌شد و ربات بالا می‌آمد؛ خرابی فقط وقتی دیده می‌شد که
بازیکن به مسیری مثل پروژهٔ شهری، نکولِ وام، پیریِ طبیعی یا «زندگی تازه» می‌رسید.

حالا دو نگهبان دارد:

| کجا | چه می‌کند |
| :--- | :--- |
| `scripts/offline-client-parity-check.cjs` | اسکیمای جاسازی‌شده، مدل‌ها، ستون‌ها و مقادیرِ همهٔ enumها را بین بستهٔ آفلاین و `prisma/schema.prisma` می‌سنجد. **بدون دیتابیس و بدون اینترنت**؛ کدِ خروج ۰ = هم‌خوان |
| `packaging.sh` (گام ۵٫۵) | همین بررسی را به‌عنوان **دروازهٔ سخت** اجرا می‌کند؛ بستهٔ ناسازگار هرگز ساخته نمی‌شود |
| `install.sh` | پس از باز کردن بسته، اسکیمای جاسازی‌شده را با `prisma/schema.prisma` مقایسه و در صورت ناسازگاری **هشدار** می‌دهد (نصب را نمی‌شکند) |

پس از هر تغییرِ `prisma/schema.prisma`، پیش از کامیت این را اجرا کنید:

```bash
node scripts/offline-client-parity-check.cjs
```

### 🕒 مهر ساخت و شناسایی «بستهٔ کهنه»

`packaging.sh` از این پس فایل `dist/BUILD_INFO.json` را با کامیت و زمانِ ساخت می‌سازد و
`install.sh` هنگام نصب/آپدیت، آن را با کامیتِ فعلی مخزن می‌سنجد. اگر کد مخزن جلوتر از بستهٔ
اجرایی باشد، هشدار زیر را می‌بینید:

```
▲ کد مخزن (a1b2c3d) با بستهٔ اجرایی (9f8e7d6) یکی نیست؛ ربات همان کد بستهٔ dist را اجرا می‌کند.
```

این هشدار **نصب را متوقف نمی‌کند** (نصب آفلاین باید در هر شرایطی کار کند)، اما معنایش این است
که برای دیدنِ کد جدید باید روی دستگاهی با npm دستور `bash offline-deps/packaging.sh` را اجرا و
بسته‌ها را commit/push کنید. اگر بسته مهر ساخت نداشته باشد (بسته‌های قبل از این نسخه)، همان
هشدار با متن «بستهٔ dist مهر ساخت ندارد» می‌آید.

### ✅ وضعیت فعلی بستهٔ منتشرشده (کامیتِ فعلی)

بسته‌های `dist.tar.gz` و `node_modules-linux.tar.gz` اکنون **از سورسِ همین کامیت ساخته
شده‌اند** (`prisma generate` + `tsc` + مهر ساخت) و هم‌خوانیِ کلاینتِ Prisma با اسکیمای
فعلی با `node scripts/offline-client-parity-check.cjs` قابلِ اثبات است — نه با فهرستِ
دستیِ نامِ انوم‌ها که کهنه می‌شود. اگر این بررسی سبز نیست، بسته منتشرشدنی نیست.

> 🧯 **تجربهٔ مکرر‌شده:** اگر بستهٔ `node_modules` بازسازی نشود (کلاینتِ کهنه) ولی
> `dist` تازه باشد، دو شکلِ خرابی دیده می‌شود. در حالتِ حاد، ربات هنگام لودِ ماژول
> می‌میرد: `TypeError: Cannot read properties of undefined (reading 'BUG')`. در
> حالتِ خفیف‌تر — که خطرناک‌تر است — ربات سالم بالا می‌آید و فقط وقتی بازیکن به
> مسیری مثل پروژهٔ شهری، نکولِ وام، پیریِ طبیعی یا «زندگی تازه» می‌رسد خطای Prisma
> می‌دهد. قاعدهٔ ساخت جدولِ بالا را فراموش نکنید: با هر تغییرِ `prisma/schema.prisma`
> **هر دو بسته** را با `bash offline-deps/packaging.sh` بازسازی و کامیت کنید.

### 🧹 پاک‌سازی کامل و نصب از صفر

```bash
cd VirtualLife                            # همان پوشه‌ای که clone کرده‌اید
bash offline-deps/install.sh reset --yes  # توقف ربات/دیتابیس + پاک‌سازیِ وضعیتِ ربات
bash offline-deps/install.sh              # نصبِ دوباره از همان بسته‌های آفلاین
```

بدون `--yes` و در ترمینالِ تعاملی، اسکریپت تأیید می‌خواهد و اگر اجرایت
غیرتعاملی است (مثلاً در CI)، بدون `--yes` **هیچ کاری نمی‌کند** و همان را می‌گوید.

**چه چیزی پاک می‌شود** (برگشت‌ناپذیر — دادهٔ بازی برنمی‌گردد):

| مسیر | چیست |
| :--- | :--- |
| `.tools/pgdata` | دیتابیسِ داخلی (بازیکن‌ها، اقتصاد، همه‌چیز) |
| `.tools/backups` | بکاپ‌های دیتابیس |
| `.tools/*.log` | لاگِ ربات، لاگِ PostgreSQL، لاگِ استقرار |
| `.tools/bot.pid` و قفل‌ها | PID و قفل‌های رهاشده (منبعِ «ربات از قبل در حال اجراست») |
| `.tools/update.state.json` | وضعیتِ آخرین استقرار |
| `.tools/.pgport`, `.tools/.pguser` | پورت و کاربرِ سرویسِ دیتابیسِ همین نصب |
| `dist/` | بستهٔ اجراییِ بازشده (دوباره از `offline-deps/dist.tar.gz` باز می‌شود) |

**چه چیزی می‌ماند:** مخزنِ کد، `prisma/`، `offline-deps/` (همراهِ دو آرشیوِ آفلاین)،
`node_modules/` و `.env` (توکن‌ها و تنظیماتِ خودتان). پس نصبِ دوباره سریع است و پرسشِ
توکن تکرار نمی‌شود. اگر ریستِ **کارخانه‌ای** می‌خواهید:

```bash
bash offline-deps/install.sh reset --yes --purge   # این دو هم می‌روند: node_modules/ و .env
```

چه چیزی به آن دست نمی‌زند: هیچ PostgreSQL یا دیتابیسِ دیگری روی این ماشین، فایل‌های
سیستم‌عامل، و کدِ پروژه. کاربرِ سرویسِ دیتابیس (اگر همین نصب ساخته باشد) فقط وقتی
حذف می‌شود که اسکریپت را با root اجرا کنید؛ در غیر این صورت همان یک خط `sudo userdel`
را برایتان چاپ می‌کند و **خودش sudo اجرا نمی‌کند**.

در پایان، اسکریپت صریحاً سنجیده می‌شود که اسکریپتِ نصب، دو آرشیوِ آفلاین و
`.env.example` سر جایشان هستند؛ اگر نباشند می‌گوید و وعدهٔ نصبِ دوباره نمی‌دهد.

اگر از دیتابیسِ خارجی (Supabase/Neon/Railway) استفاده می‌کردید، خودِ سرورها را هم از
همان پنل حذف کنید؛ اسکریپتِ نصب به آن‌ها دست نمی‌زند.

### راستی‌آزمایی بسته پیش از انتشار

همهٔ این اسکریپت‌ها روی PostgreSQL زنده اجرا می‌شوند و فقط به دیتابیسِ با پسوند
`_ux_test` دست می‌زنند (دادهٔ آزمایشی می‌سازند و پاک می‌کنند). بین هر اجرا
دیتابیس را تازه بسازید تا ادعاها روی وضعیتِ تمیز سنجیده شوند:

> آدرس را در یک **زیرپوسته** بدهید (یا به‌شکل پیشوندِ همان‌خط)، نه با `export`
> سراسری در ترمینال: یک `export` جامانده به نصب/آپدیتِ بعدی ارث می‌رسد و آن را روی
> دیتابیسِ اشتباه می‌برد. زیرپوسته با پایان یافتنش پاک می‌شود و چیزی باقی نمی‌گذارد.

```bash
(
  export DATABASE_URL="postgresql://virtual_life@127.0.0.1:5433/legacy_ux_test"

  node scripts/offline-client-parity-check.cjs    # (بدون دیتابیس) کلاینتِ بسته ↔ schema.prisma
  node offline-deps/scripts/migrate.js .          # اعمال مهاجرت‌ها
  node scripts/offline-bundle-verify.cjs          # خودِ بستهٔ منتشرشده: کلاینت + dist + مهاجرت‌ها
  node scripts/admin-moderation-smoke.cjs         # اخطار، مسدودسازی خودکار، حذف حساب و یکپارچگی کلیدهای خارجی
  node scripts/admin-ux-smoke.cjs                 # دسترسی ادمین اصلی/دوم و اتمیک‌بودن نوشتارهای مالی
  node scripts/marriage-live-smoke.cjs            # قانون مهریه، پذیرش صریح، جابه‌جایی دقیق پول، رقابت و طلاق
  node scripts/gameplay-live-smoke.cjs            # شیفت و مالیات، بانک، کسب‌وکار و حقوق، ثبت گروه و سطح محیط، تحصیل و مهارت
  node scripts/economy-race-smoke.cjs             # کلیکِ پشت‌سرهم روی هر دکمهٔ پول: هفتهٔ پرداخت‌شده = هفتهٔ تحویل‌شده، و هرچه از صندوق رفت به جیب رسید
  node scripts/reward-burn-smoke.cjs              # تزریقِ خطا: اگر پرداخت وسط کار بمیرد، ادعا نباید ثبت بماند و تلاشِ دوباره باید دقیقاً یک‌بار بپردازد
  node scripts/economy-invariants-smoke.cjs       # یک روزِ کاملِ بازی از مسیرِ واقعیِ سرویس‌ها، بعد ممیزی: ترازنامهٔ بانک بسته بماند، داراییِ هر بازیکن تا ریال با دفتر کل بخواند، و هیچ صندوقی منفی نباشد
)
```

### ممیزِ اقتصاد روی دیتابیسِ واقعی (فقط‌خواندنی)

`offline-deps/scripts/economy-audit.js` همان سه پرسش را روی هر دیتابیسی — از جمله
دیتابیسِ واقعیِ سرور — جواب می‌دهد و هیچ نوشتنی نمی‌کند: چقدر پول وجود دارد و کجا
نشسته، ترازنامهٔ بانک بسته است، و داراییِ خصوصیِ هر بازیکن (کیف پول + حسابِ
بانکی) با دفتر کلِ او می‌خواند. فقط به `pg` و `dist/modules/economy/money-supply.js`
نیاز دارد، پس روی سرورِ آفلاین هم اجرا می‌شود:

```bash
node offline-deps/scripts/economy-audit.js      # کد خروج ۰ = سالم، ۱ = اختلاف (برای پایش)
```

اختلافِ گزارش‌شده یعنی یک مسیرِ مالی پول را بدونِ ردیفِ دفتر کل جابه‌جا کرده (یا
برعکس). توجه: این ابزار برای دیتابیسِ *واقعی* است؛ در دیتابیسِ آزمونِ مهارها که
موجودیِ بعضی شخصیت‌ها با دست کاشته می‌شود، همان شخصیت‌ها را به‌درستی «اختلاف»
گزارش می‌کند.

این سه اسکریپت سه پرسشِ جدا را می‌پرسند: `economy-race-smoke` رقابتِ درخواست‌های
همزمان را می‌آزماید (جایی که مقدار پیش از تراکنش حساب شده یا بازندهٔ رقابت به‌جای
پرتاب `return` می‌کند)، `reward-burn-smoke` مرگِ پرداخت را (جایی که ردیفِ ادعا
بیرون از تراکنشِ پرداخت نوشته می‌شود و پاداش برای همیشه می‌سوزد)، و
`economy-invariants-smoke` هم‌خوانیِ کلِ اقتصاد را پس از یک روزِ کاملِ بازی
(ترازنامهٔ بانک، آشتیِ دفتر کل با داراییِ بازیکن، و منفی‌نشدنِ هیچ صندوقی).
هر سه از `economy-invariants-smoke` به بعد نیازی به دادهٔ دست‌ساز ندارند: پولِ
بازیکنان از مسیرِ واقعیِ پنل ادمین می‌آید تا خودش ردیف دفتر کل بگذارد.

### ساختِ کلاینت در محیطِ توسعهٔ بدون اینترنت

`npm ci` / `npm install` کلاینت Prisma را **به‌شکل خام (stub)** می‌گذارد و
`npm run build` می‌خواهد موتور را از `binaries.prisma.sh` بگیرد؛ در محیطِ بدون
اینترنت شکست می‌خورد و نشانه‌اش خطاهایی مثل
`Module '"@prisma/client"' has no exported member 'Gender'` است. موتورِ اسکما
داخل خودِ مخزن است (`prisma-engines/`) و Prisma آن را spawn می‌کند، پس باید
یک کپیِ **اجرایی** در مسیر موقت ساخته شود:

```bash
SE="$(mktemp -d)/schema-engine"
cp prisma-engines/schema-engine.gz "$SE" && chmod +x "$SE"
export PRISMA_SCHEMA_ENGINE_BINARY="$SE"
export DATABASE_URL="postgresql://dummy:dummy@localhost:5432/dummy"
node node_modules/prisma/build/index.js generate   # سپس: npx tsc
```

`offline-deps/packaging.sh` همین ترتیب را به‌شکل خودکار انجام می‌دهد.

## 🩺 عیب‌یابی

### خطای «Cannot change ownership to uid … : Invalid argument» هنگام نصب
این خطا از `tar` است و معنایش این است که آرشیو (مثلاً `dist.tar.gz`) روی دستگاه دیگری
ساخته شده و `uid/gid`ِ کاربرِ آن دستگاه در سرور مقصد — به‌ویژه در کانتینرهای با
user namespace محدود — قابل تنظیم نیست؛ `tar` هنگام `chown` با `Invalid argument`
خطا می‌دهد و اسکریپت (به‌خاطر `set -e`) قبل از راه‌اندازی ربات قطع می‌شود.

نسخهٔ فعلی اسکریپت‌ها این مشکل را **خودکار** حل می‌کند:
- `install.sh` همهٔ `tar`ها را با `--no-same-owner` اجرا می‌کند (فایل‌ها به مالکیتِ
  کاربرِ اجرای اسکریپت می‌افتند).
- `packaging.sh` آرشیوهای جدید را با صاحبِ نرمال‌شدهٔ `0/0` می‌سازد تا اصلاً
  `uid` دستگاه سازنده در آرشیو ذخیره نشود.

اگر روی سرور نسخهٔ قدیمی `install.sh` را دارید، بعد از `git pull` دوباره اجرا کنید.
راه‌حلِ سریعِ موقت **بدون** آپدیت، روی خودِ سرور:

```bash
sed -i 's/tar xJf/tar --no-same-owner -xJf/; s/tar xzf/tar --no-same-owner -xzf/' offline-deps/install.sh
bash offline-deps/install.sh
```
